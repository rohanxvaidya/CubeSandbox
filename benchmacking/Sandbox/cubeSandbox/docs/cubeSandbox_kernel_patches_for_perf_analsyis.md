# CubeSandbox Kernel Patch Bisect Analysis for Latency Improvement

## 1. 调查背景与目标

**目标**：由于 `cubesandbox` benchmark 中 `create.avg` 延迟在较新内核中发现有明显差异，本次调查的目的是在 Linux Kernel `v6.17` 到 `v6.18-rc1` 周期内，准确定位使得 `create.avg` 性能显著好转（延迟降低且稳定达到基准线）的具体代码补丁（Commit）。

**性能标准设定**：
*   **满血达标（快）**：连续 3 轮测试的均值在 `~200ms` 上下且不超过 `205ms`，同时失败率/完成率指标保持稳定。
*   **未达标（慢）**：延迟突破 `240ms` (常常在 `245ms ~ 248ms` 区间浮动)。

---

## 2. 第一阶段：隔离次分支并探索主干 (Mainline Bisect)

在常规的 Git Bisect 中，测试曾深入到带有大量 `6.17.0-rc*` 时间戳的内部合并记录而迷失。原因在于并行开发模型：许多外部子系统的补丁在 `6.17` 之前被编写打包，但直到 `v6.18-rc1` 开始的“Merge Window (合并窗口)”才最终插进主树。

为了获得全局正确的时间线，引入了 `git bisect start --first-parent` 参数。这要求查找脚本仅仅验证被“推入”历史主干线的**主合并节点 (Merge Commits)**，完全无视它们的编写发生时间。

**通过主干二分法：**
在锁定 `< 205ms` 的新阈值后，我们找到了主链路上产生“性能跳水”（从慢到快大幅度好转）的真实核心分水岭节点：
*   **最晚的“慢”节点 (均值约 243.5ms)：**
    `bf897d2626abe4559953342e2f7dda05d034c8c7` (Merge tag 'for_linus' / vhost 相关)
*   **最早的“快”节点 (均值跌落并稳在 198.9ms)：**
    `f3826aa9962b4572d01083c84ac0f8345f121168` (Merge tag 'for-linus' / kvm 虚拟化综合性更新合集)

**第一阶段结论：** 确准由 `f3826aa9` 这个包含了约 178 个底层 KVM 修订的包袱在并入主干时引起了 `cubesandbox` 测试框架的改善。

---

## 3. 第二阶段：深入旁支定位具体的行级代码 (Sub-Branch Micro Bisect)

在找到了引发该现象的 `178` 个补丁包袱（合并状态）后，调查剥离了主干过滤限制。我们让测试程序专门在 `bf897d26` (慢) 到 `f3826aa9` (快) 这个封装区间内逐层剥叠，深入到了其底层旁侧分支内部署深度探测测试。

在这个旁枝二分过程中，测试编译出的多款内核在名字后带着当年被拉取时的 `rc3`/`rc4` 后缀标志。测试最终在这个微小代码层面上抓获了真正的改变转折子节点。

**确切的单层转折分支（第一代“快”分叉合集）:**
`181ce6b01ad52aeb791545edbae0b92648c6428d`
> `Merge branch kvm-arm64/misc-6.18 into kvmarm-master/next`

在这一极窄的合并区域内发生性能改变的 `kvm-arm` 子分支中，我们锁定了两个极具嫌疑可能实际阻碍宿主机内存请求释放效率从而严重影响到宿主环境乃至特定调用的补丁行为：
1.  **`5f9466b50c1b`**  `KVM: arm64: Fix page leak in user_mem_abort()`
    **(关键行级影响)**：修正了由不匹配的属性触发失败映射动作而产生的内核页引用内存泄漏。这有可能清除了宿主机中某种因为异常引用产生的资源停滞效应（从先前的子系统 247.9ms 测试降低到并入时的 202.5ms）。
2.  **`8673e5b22e1e`**  `KVM: arm64: ptdump: Don't test PTE_VALID alongside other attributes`

---

## 4. 最终总结以及如何建立手动验证对照组

本次分析成功地找出了使得 cubesandbox 成绩从 `~245ms` 区间回降到 `<205ms` 的代码发生点，并归因到了针对硬件内存错误回收机制的一组底层修改上。

如果工程师需要针对此事件开启隔离性的手控变量验证或开展基于这行代码本身影响力的后续剖析，可基于远端节点采取下面方案：

**重现性能悬殊对比的手测方式：**
1.  在 `/home/mz/kernel/v6p17` 重置任何 git 状态 (`git reset --hard` && `git bisect reset`)。
2.  签出包含未被 `misc` 分支代码干预修正的遗留状态代码：`git checkout 5f9466b50c1b` (这将作为一个慢验证组)。
3.  编译生成 `kernelrelease` 以及配套安装（`make modules_install && make install`）并用机器对应的 `/usr/local/sbin/kernel-default` 接管其启动项目。
4.  重启机器测出性能确认值达到较慢的 >245ms。
5.  同法签出 `git checkout 181ce6b01ad5` 来构建快验证对照组，并验证数据能大幅降低归于 `202ms` 以内，验证这层合并的物理影响。
